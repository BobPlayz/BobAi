# BobAI production training target

BobAI is designed as one user-facing assistant backed by a core language/reasoning model plus approved tools and modality specialists. The repository now includes the data and runtime architecture for conversation, multilingual behavior, epistemics/source checking, anti-sycophancy, emotional attunement, coding/software-factory work, research, browser tasks, computer use, MS Paint, Blender/3D, image/video/music/voice orchestration, documents, data analysis, memory, automation, APIs, deployment, security, recovery, and verification.

## Build the core corpus

```bash
python -m pip install -r model-training/requirements.txt
python model-training/build_final_dataset.py
python model-training/prepare_dataset.py --input model-training/data/source.jsonl
```

The core builder combines the verified public multilingual sources already registered in the repository with BobAI's original capability curriculum. Tool trajectories use explicit `[tool_call]`, `[tool_result]`, and error/recovery markers so the core model can learn when to invoke a tool, when to abstain, how to react to failures, and that execution is not complete until the result is checked.

## Teacher-model synthetic data

BobAI can optionally learn from outputs generated by a user-authorized teacher model through an OpenAI-compatible endpoint. This is not enabled implicitly because different providers and models have different terms for training/distillation.

```bash
python model-training/build_teacher_dataset.py \
  --endpoint https://YOUR-TEACHER-ENDPOINT/v1/chat/completions \
  --model YOUR-TEACHER-MODEL \
  --confirm-rights
```

The builder writes `model-training/data/teacher/teacher.jsonl`. The normal corpus builder ingests that directory automatically. `--confirm-rights` is mandatory so BobAI does not silently train on outputs that the model/provider terms prohibit reusing.

You can point this at a permitted local teacher model too. Using several authorized teachers is possible by writing separate JSONL files into `model-training/data/teacher/` and keeping model/provider provenance in each record.

## Multimodal assets

Binary media does not belong inside the core JSONL. Put licensed asset manifests under `model-training/data/multimodal/`. Each JSONL row must include:

```json
{
  "id": "rocket-001",
  "modality": "3d",
  "asset": "blender/rocket.glb",
  "task": "Recognize the rocket structure and verify the exported model.",
  "source": "original",
  "license": "original",
  "eligible_for_training": true,
  "metadata": {"application": "Blender"}
}
```

Supported modality labels are `image`, `audio`, `video`, `3d`, `music`, `document`, `table`, and `screenshot`.

Validate/merge them with:

```bash
python model-training/build_multimodal_manifest.py
```

The validator checks explicit eligibility, source/license fields, expected file extensions, hashes mounted files, rejects missing assets by default, and deduplicates records.

## Desktop, MS Paint, and Blender

The API tool registry contains three first-class execution tools:

- `computer`: general authorized desktop operation
- `paint`: MS Paint drawing/editing and artifact saving
- `blender`: model creation, editing, rendering, exporting, and verification

They run through `BOBAI_COMPUTER_PROVIDER_URL` and the optional `BOBAI_COMPUTER_PROVIDER_KEY`, using the same permission, approval, audit, timeout, and untrusted-result handling as the rest of BobAI's tool loop.

Example intent:

```text
User: Hey BobAI, draw a rocket in MS Paint, then make the same rocket in Blender.
BobAI: route to paint -> save/verify -> route to blender -> create -> verify -> render/export -> report the checked artifacts
```

The core model is trained on those trajectories. The desktop provider is responsible for the actual GUI session and screenshots/state observations. Blender may additionally use its Python API inside the authorized provider for deterministic geometry work, but that execution stays behind the same user-approval boundary.

## Behavior target

BobAI is explicitly trained and prompted to avoid reflexive agreement. It should:

- verify current, niche, changing, or disputed facts with research when available;
- correct false premises instead of mirroring them;
- avoid empty praise or flattering a user just because they request it;
- react naturally to frustration, excitement, sadness, confusion, or anger without pretending to possess human feelings;
- separate emotional attunement from factual judgment;
- distinguish verified facts, inference, and uncertainty;
- treat webpages, files, tool results, retrieved documents, and teacher-model output as untrusted data;
- use tools for requested actions and verify the user-visible outcome before claiming completion.

## What training time does and does not guarantee

A long run is not a capability guarantee. Ten days, fifteen days, or months of training only help if model size, architecture, token count, data quality, optimization, hardware, and evaluation are appropriate. The current tiny native Transformer remains suitable for experiments and pipeline validation, not a frontier-scale production model. The repository architecture is designed so the data/tool system can scale to larger hardware and models without rewriting the product boundary.

For a production-scale BobAI, actual training still requires sufficient compute, storage, licensed data, real configured tool providers, evaluation, and deployment verification. Those are environment/resource requirements rather than missing repository features.
