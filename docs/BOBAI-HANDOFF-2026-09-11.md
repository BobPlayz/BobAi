# BobAI handoff — 2026-09-13

BobAI is organized around the public model family Bob, Forge, Vanta, Echo, Flux, and Vector. Bob is the main text model, Forge is the coding model, Vanta handles vision and reranking, Echo handles speech, Flux handles image generation, and Vector handles embeddings. Bob Core is an internal orchestration concept only. Ordinary users are not given scheduler or runtime-registry state through normal model APIs, while the runtime inspection surface is protected by the existing admin boundary.

Repository-side AI infrastructure now includes the native Bob training and inference path, specialist training kits, specialist dataset preparation, authenticated local specialist workers, checkpoint existence checks, bounded worker requests and responses, runtime leases, resource-aware runtime bookkeeping, local research/search fallbacks, retrieval reranking, and local media boundaries. The native text trainer is built for long experiments with resumable latest and best-validation checkpoints, gradient accumulation, cosine learning-rate scheduling, early stopping controls, architecture validation, evaluation, and portable model export. Specialist training covers Vector, Vanta, Echo, Flux, and reranking, with ASR CTC handling and TTS audio feature preparation included.

BobHS now has repository-side controller and node foundations for authenticated registration, heartbeats, capability and model inventory, resource-aware placement, deployment leases, draining, Docker execution bounds, persistent volume declarations, atomic local state writes, and lifecycle status. Scheduler selection has tests. Additional reusable BobHS runtime primitives now cover durable file-backed job state, idempotency-key deduplication, worker claims, expiring leases, retry and cancellation semantics, worker draining, reference-counted model lifecycle, idle eviction, graceful shutdown, queue backpressure policy, retry jitter, bounded runtime event buffering, optimistic shared-state versioning, rolling deployment planning, and SHA-256 model artifact verification. The durable queue is now Windows-path-safe and serializes file mutations with a filesystem lock so separate BobHS processes sharing the same queue file cannot claim or enqueue the same work concurrently. Model startup is also coordinated so concurrent acquires share one startup operation instead of racing. Regression coverage now exercises these behaviors and the BobHS package test command runs every test file.

The BobHS CI path now uses Node 24 to match the package engine and runs the expanded test glob through the existing repository validation workflow. These are repository-side checks and concurrency hardening, not proof of real multi-node production behavior. The remaining Phase 5 item is still the wiring of these primitives through every live BobHS execution path plus verification in the target environment.

The roadmap has been reorganized into ten phases. Phase 1 is the basic foundation, Phase 2 is the local AI core, Phase 3 is the specialist family, Phase 4 is runtime and security, Phase 5 is BobHS local orchestration, Phase 6 is training and verification of every model, Phase 7 is native media and multimodal runtime, Phase 8 is production BobHS, Phase 9 is production security and reliability, and Phase 10 is production scale. roadmap.md remains checklist-only. The repository-side Phase 5 regression-coverage item is complete, while live execution-path integration and environment verification remain open.

No trained model checkpoint is being claimed as complete yet. The current architectures are from-scratch research baselines, so running for seven days or longer can be useful, but training time alone cannot guarantee that they will beat every other local model. Model quality will depend on the actual dataset, architecture, tokenizer, training procedure, evaluation results, and the hardware available. The goal is to push quality as far as the available compute and data realistically allow rather than pretending that a time limit guarantees perfection.

The code-side repository work should be treated as preparation for real training and real environment verification, not as proof that the target Windows machine, native media libraries, model weights, SMTP, OAuth callbacks, production hosting, hardware performance, or multi-node deployment have been tested. Those require the user's environment. The intended target machine is the user's Windows laptop, and long training runs may take days or longer depending on the chosen model and dataset.
