# BobAI handoff — 2026-09-12

This pass completes the repository-side model architecture expansion for the user's local-first, from-scratch AI goal. Bob-0.2-native remains the central text brain: it is a configurable decoder-only transformer trained from scratch, uses a 261-token UTF-8 byte tokenizer, supports configurable context, width, depth, attention heads, feed-forward width, AdamW training, gradient clipping, CPU/CUDA selection, validation loss reporting, and the portable model.bob v2 format. The Node runtime reads the architecture from the model header and performs causal attention directly in Node.js. No Ollama process, URL, environment variable, or fallback inference server is part of the chat path.

The repository now also contains a from-scratch specialist training kit for modalities and tasks that cannot be obtained by training the text transformer alone. The kit defines small CPU-friendly baselines for text embeddings, retrieval reranking, RGB vision encoding, CTC speech recognition over log-mel features, text-to-mel speech synthesis, and a tiny 32x32 text-conditioned image generator. A bounded specialist CLI validates tensor dataset shapes, trains with AdamW and gradient clipping, rejects non-finite loss, and writes model metadata with checkpoints. These are explicitly research-scale starting architectures for the target laptop, not claims of production parity with large pretrained speech, vision, or image systems. The image baseline still needs a proper decoder/vocoder boundary for practical media, and each specialist still needs an application runtime before BobAI can invoke it as a first-class production capability.

The training kit remains source-first. The main text pipeline contains eligibility, consent, secret and basic PII sanitization, deterministic deduplication, and held-out splits. Specialist datasets must be prepared locally under the same eligibility and privacy rules. Model weights remain deployment artifacts and are not committed to the repository. A small checked-in text dataset is only a development proof; the target machine must receive a substantially larger eligible dataset before a serious training run. A one-to-two-day CPU run can produce an experiment, but duration alone cannot turn a small architecture into a frontier model.

The media architecture remains on the BobAI-owned native boundary. BobMedia is a Node-API addon contract, BobVoice calls the Piper C API in-process, BobWhisper calls the whisper.cpp C API in-process, and BobMedia performs native PCM16 WAV probing without spawning Piper, whisper-cli, FFmpeg, ffprobe, or a shell. The current native media core intentionally supports PCM16 WAV only. MP3, MP4, WebM, AAC, H.264, and other codecs still require native codec implementations; those are algorithms and should not be replaced by pretending to train a language model to decode them.

The normal TypeScript CI build does not build the native media addon because its native libraries and model weights are deployment artifacts. The target Windows machine remains the verification boundary for Visual C++ tooling, native dependency linkage, model loading, speech/media workloads, and performance. The specialist model runtime integration is also a target-machine/application integration boundary and has not been marked complete merely because training code exists.

BobHS remains repository-foundation code and still needs production ingress/TLS, durable shared controller state, capacity-aware scheduling, persistent volumes, registry integration, rolling deployment behavior, logs, backups, domains, and verified failover before those capabilities can be called production-complete. Real SMTP, social-provider callbacks, sandbox runtime verification, model training, specialist training, native media verification, hosting/DNS, and target-hardware performance also remain environment-dependent. Before every future commit, roadmap.md and this handoff must both be updated. roadmap.md remains checklist-only and this handoff remains paragraph-only.
