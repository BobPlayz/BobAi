BobAI remains a single user-facing assistant with a central tool-policy boundary, a compact development model, and a separate scalable production-model path. Repository work covers bounded tool execution, approvals, validation, cancellation, network-target checks, provider limits, bundle integrity, media limits, result limits, agent-plan bounds, repository preflight, CI, production readiness privacy, memory/tool safeguards, coding orchestration, research, browser/document/data/media capabilities, first-class computer use, MS Paint, Blender/3D, anti-sycophancy, source checking, calibrated uncertainty, emotional attunement without fake praise, failure recovery, verification, a capability-oriented multilingual corpus builder, a validated multimodal asset-manifest pipeline, and rights-gated teacher-model distillation.

The main runtime exposes `computer`, `paint`, and `blender` tools behind the existing permission, approval, audit, timeout, and untrusted-result handling. They execute through BOBAI_COMPUTER_PROVIDER_URL with an optional BOBAI_COMPUTER_PROVIDER_KEY. Blender supports create_model, edit_model, render, export, and verify intents. The tool router prefers research for current, changing, niche, disputed, or externally verifiable factual claims and uses execution tools when the user asks BobAI to actually operate software or create an artifact. The chat system prompt rejects reflexive agreement and empty praise, corrects unsupported premises, distinguishes fact/inference/uncertainty, reacts naturally to the user's emotional context without pretending to possess human feelings, treats external content as untrusted, and requires result verification before completion claims.

The production training stack now has two model lanes. `bob-0.2-native` remains the tiny byte-level laptop/dev sanity model. `bob-production` is a separate from-scratch scalable Transformer using RoPE, RMSNorm, SwiGLU, grouped-query attention, PyTorch scaled-dot-product attention/Flash Attention where supported, tied embeddings, optional gradient checkpointing, a trainable byte-level BPE tokenizer, mixed precision, gradient accumulation, cosine warmup/decay, resumable checkpoints, validation, and torchrun/DDP multi-GPU training. Production profiles are provided from a small dev configuration through 125M, 350M, 1.3B, and 3B-class configurations. The local Node model provider can automatically use `bob-production` when its tokenizer and checkpoint exist. It launches `production_model_server.py` on localhost with a random bearer token, bounded requests/responses, configurable device/port/path settings, and falls back to the compact native model only when production artifacts are absent and production was not explicitly required.

The production training workflow is documented in `model-training/PRODUCTION_TRAINING.md`. `train_tokenizer.py` builds the production BPE tokenizer from prepared BobAI conversations. `train_production.py` trains the scalable model. `production_model.py` defines the architecture and generation path. `production_model_server.py` provides the local inference worker. `productionModelRuntime.ts` connects that worker to the API. `build_final_dataset.py` merges the verified public multilingual sources, original BobAI capability curriculum, and explicitly eligible teacher JSONL under `model-training/data/teacher`. `build_teacher_dataset.py` can generate synthetic examples from a user-configured OpenAI-compatible teacher endpoint only when `--confirm-rights` is passed. `build_multimodal_manifest.py` validates mounted licensed image/audio/video/3D/music/document/table/screenshot assets, source/license metadata, compatible extensions, file hashes, and deduplication. CI compiles and unit-tests the new production-model and capability-training sources.
