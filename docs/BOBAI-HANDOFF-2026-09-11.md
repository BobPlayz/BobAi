# BobAI handoff — 2026-09-12

This pass added the first real BobHS self-hosting layer inside the repository. BobHS is a separate workspace named `@bobai/bobhs` with controller and node-agent modes. The controller persists node and deployment state to a local 0600 JSON state file, authenticates administration with a controller token, bootstraps nodes through a separate join token, stores only SHA-256 hashes of node tokens, exposes authenticated node heartbeats, and atomically claims queued deployments by assigning them to the node before returning work. The node agent requires a controller URL, node ID, and node token and polls for assignments while reporting heartbeats and deployment results.

The first execution backend is Docker. BobHS launches trusted images through `execFile` rather than a shell, validates image/name/environment/port inputs, applies bounded CPU and memory settings, caps PIDs, drops all Linux capabilities, enables no-new-privileges, uses a read-only container root, and provides a bounded tmpfs. No arbitrary host mounts, privileged mode, Docker socket mounts, or shell command strings are accepted by the deployment API. Docker is therefore an optional node runtime for BobHS rather than a dependency of the BobAI core API.

The root workspace now exposes `npm run bobhs`, `npm run bobhs:build`, and `npm run bobhs:start`, and the root environment template contains the BobHS controller/node settings without secrets. `apps/bobhs/README.md` documents the controller bootstrap, node registration, deployment API, security model, and current limitations. The roadmap records the BobHS foundation as implemented while leaving production ingress, TLS, database-backed state, scheduling, volumes, registry, rolling deployment, logs, backups, and failover explicitly unverified.

The BobHS runtime has not been executed in this environment, and no Docker-backed deployment has been claimed as verified. The next required validation is a real local controller build/start, node registration, Docker availability check, test-container deployment, status transition, stop behavior, and restart persistence. Public hosting still requires a real reachable machine, TLS/ingress, persistent storage, monitoring, backups, and production hardening; BobHS is the software foundation that removes dependence on a specific commercial hosting provider rather than a claim that physical compute can be free without hardware.

Before every future commit, roadmap.md and this handoff must both be updated. roadmap.md must remain checklist-only and this handoff must remain paragraph-only. Unverified build, test, provider, deployment, runtime, hardware, and environment work must never be represented as completed merely because the repository contains the corresponding implementation.
